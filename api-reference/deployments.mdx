The Deployments API lets you trigger new builds of your documentation site, track build progress, and integrate deployment status into your CI/CD pipelines. When you trigger a deployment, SBGDS builds and publishes your latest content, making it live at your project's URL.

## The Deployment Object

All Deployments endpoints return deployment objects with the following fields.

<ResponseField name="id" type="string">
  The unique identifier for the deployment.
</ResponseField>

<ResponseField name="status" type="string">
  The current state of the deployment. One of `pending`, `building`, `live`, or `failed`.
</ResponseField>

<ResponseField name="url" type="string">
  The public URL where the deployed documentation site is accessible. Only populated when `status` is `live`.
</ResponseField>

<ResponseField name="branch" type="string">
  The source branch that was deployed (for example, `main` or `docs/update-api-guide`).
</ResponseField>

<ResponseField name="createdAt" type="string">
  ISO 8601 timestamp indicating when the deployment was triggered.
</ResponseField>

### Deployment status lifecycle

A deployment moves through the following states in order:

| Status | Description |
|---|---|
| `pending` | The deployment has been queued and is waiting for a builder to pick it up. |
| `building` | SBGDS is actively building and processing your documentation content. |
| `live` | The build succeeded and the site is publicly accessible at the deployment `url`. |
| `failed` | The build encountered an error. Check the deployment logs in the dashboard for details. |

## List Deployments

Retrieve all deployments for a project, ordered by creation time with the most recent first.

```text
GET /v1/projects/{projectId}/deployments
```

### Path parameters

<ParamField path="projectId" type="string" required>
  The unique identifier of the project whose deployments you want to list.
</ParamField>

### Query parameters

<ParamField query="limit" type="integer">
  Number of deployments to return. Defaults to `20`, maximum `100`.
</ParamField>

<ParamField query="after" type="string">
  Cursor for next-page navigation. Pass the `endCursor` from a previous response.
</ParamField>

<ParamField query="status" type="string">
  Filter results to a specific deployment status. One of `pending`, `building`, `live`, or `failed`.
</ParamField>

### Example request

```bash
curl "https://api.sbgds.com/v1/projects/proj_abc123/deployments?limit=5" \
  -H "Authorization: Bearer sk_live_..."
```

```javascript
const response = await fetch(
  "https://api.sbgds.com/v1/projects/proj_abc123/deployments?limit=5",
  { headers: { Authorization: "Bearer sk_live_..." } }
);
const { data, meta } = await response.json();
```

### Example response

```json
{
  "data": [
    {
      "id": "dep_7f8g9h",
      "status": "live",
      "url": "https://docs.yourcompany.com",
      "branch": "main",
      "createdAt": "2024-04-11T14:00:00Z"
    },
    {
      "id": "dep_4d5e6f",
      "status": "failed",
      "url": null,
      "branch": "docs/update-api-guide",
      "createdAt": "2024-04-10T11:30:00Z"
    }
  ],
  "meta": {
    "hasNextPage": false,
    "hasPreviousPage": false,
    "startCursor": "cursor_7f8g9h",
    "endCursor": "cursor_4d5e6f"
  }
}
```

## Get a Deployment

Retrieve the current status and details of a single deployment. Poll this endpoint to track build progress, or use [webhooks](#webhook-events) to receive status changes automatically.

```text
GET /v1/projects/{projectId}/deployments/{deploymentId}
```

### Path parameters

<ParamField path="projectId" type="string" required>
  The unique identifier of the project that contains the deployment.
</ParamField>

<ParamField path="deploymentId" type="string" required>
  The unique identifier of the deployment to retrieve.
</ParamField>

### Example request

```bash
curl https://api.sbgds.com/v1/projects/proj_abc123/deployments/dep_7f8g9h \
  -H "Authorization: Bearer sk_live_..."
```

```python
import httpx

headers = {"Authorization": "Bearer sk_live_..."}
r = httpx.get(
    "https://api.sbgds.com/v1/projects/proj_abc123/deployments/dep_7f8g9h",
    headers=headers,
)
deployment = r.json()
```

### Example response

```json
{
  "id": "dep_7f8g9h",
  "status": "live",
  "url": "https://docs.yourcompany.com",
  "branch": "main",
  "createdAt": "2024-04-11T14:00:00Z"
}
```

<Tip>
  If you need to poll for deployment completion, check the `status` field every 5–10 seconds and stop once it reaches `live` or `failed`. For production workloads, prefer webhooks to avoid unnecessary requests.
</Tip>

## Trigger a Deployment

Start a new deployment for a project. SBGDS builds your documentation from the specified branch and publishes the result.

```text
POST /v1/projects/{projectId}/deployments
```

### Path parameters

<ParamField path="projectId" type="string" required>
  The unique identifier of the project to deploy.
</ParamField>

### Body parameters

<ParamField body="branch" type="string">
  The branch to deploy. Defaults to the project's production branch (usually `main`) if omitted.
</ParamField>

<Note>
  Triggering a deployment while another deployment for the same project is in the `building` state queues your new deployment — it will begin once the current build finishes.
</Note>

### Example request

```bash
curl -X POST https://api.sbgds.com/v1/projects/proj_abc123/deployments \
  -H "Authorization: Bearer sk_live_..." \
  -H "Content-Type: application/json" \
  -d '{"branch": "main"}'
```

```javascript
const response = await fetch(
  "https://api.sbgds.com/v1/projects/proj_abc123/deployments",
  {
    method: "POST",
    headers: {
      Authorization: "Bearer sk_live_...",
      "Content-Type": "application/json",
    },
    body: JSON.stringify({ branch: "main" }),
  }
);
const deployment = await response.json();
console.log(`Deployment ${deployment.id} is ${deployment.status}`);
```

### Example response

```json
{
  "id": "dep_1k2l3m",
  "status": "pending",
  "url": null,
  "branch": "main",
  "createdAt": "2024-04-12T09:00:00Z"
}
```

A successful trigger returns `201 Created`. The deployment begins in `pending` status and progresses to `building` shortly after.

## Webhook Events

Instead of polling the Get a Deployment endpoint, subscribe to webhook events to receive real-time notifications whenever a deployment's status changes. Configure webhooks from **Settings → Webhooks** in the dashboard.

SBGDS sends an HTTP `POST` request to your webhook URL with a JSON body for each of the following events.

### Event types

| Event | Trigger |
|---|---|
| `deployment.pending` | A new deployment has been queued. |
| `deployment.building` | The deployment has started building. |
| `deployment.live` | The deployment succeeded and the site is live. |
| `deployment.failed` | The deployment failed during the build. |

### Webhook payload

Every webhook delivery includes an `event` field identifying the event type, a `deployment` object with the current deployment state, and a `projectId` indicating which project the deployment belongs to.

```json
{
  "event": "deployment.live",
  "projectId": "proj_abc123",
  "deployment": {
    "id": "dep_1k2l3m",
    "status": "live",
    "url": "https://docs.yourcompany.com",
    "branch": "main",
    "createdAt": "2024-04-12T09:00:00Z"
  }
}
```

### Verifying webhook signatures

SBGDS signs every webhook request with an HMAC-SHA256 signature using your webhook secret. Verify the `X-SBGDS-Signature` header to confirm the request originated from SBGDS.

```javascript
import crypto from "crypto";

function verifyWebhook(payload, signature, secret) {
  const expected = crypto
    .createHmac("sha256", secret)
    .update(payload)
    .digest("hex");
  return crypto.timingSafeEqual(
    Buffer.from(expected),
    Buffer.from(signature)
  );
}
```

<Warning>
  Always verify webhook signatures before processing the payload. Skipping this check lets anyone send arbitrary events to your webhook endpoint.
</Warning>

### Responding to webhooks

Return a `2xx` HTTP status code within **10 seconds** to acknowledge receipt. If SBGDS does not receive a `2xx` response in time, it retries the delivery with exponential backoff, up to **5 attempts** over approximately 24 hours.
